# Performance measurement

How protohoggr's performance is measured, why the method is shaped the way it
is, and what it has found. The library's contract is speed on well-formed
protobuf data, so every workload here is well-formed input generated by the
crate's own encoders.

Every build and every benchmark run goes through `brokkr`. The tools below
are written so that no step needs raw `cargo` or `rustc`.

## Build profile: fat LTO, one codegen unit

`[profile.release]` in the root `Cargo.toml` sets `lto = "fat"` and
`codegen-units = 1`; the bench profile inherits it, and `brokkr run` builds
release by default. That is how the crate's consumers build it: pbfhogg and
elivagar both ship with fat LTO and one codegen unit. A measurement under
cargo's default release profile (thin local LTO, 16 codegen units) describes
code nobody ships: inlining across the crate boundary, the placement of
out-of-line paths such as the cold varint continuation, and the final code
layout all differ. Dependents never read a dependency's profiles, so the
setting costs consumers nothing; its cost is slower release builds here,
`brokkr test` included.

elivagar also builds with `panic = "abort"`, which changes landing pads and
therefore code size and layout even on paths that never panic. The
`release-abort` profile adds it, for runs of the `ab` example
(`brokkr run ab --profile release-abort -- time`). Cargo ignores `panic` for
bench targets, so criterion results are always unwind builds.

## Criterion benchmarks

`bench/` is an unpublished workspace member (`protohoggr-bench`), outside the
library's dependency tree. Its bench targets measure the working tree:

| Target | Groups | Inputs |
|---|---|---|
| `varint` | `decode_sint64`, `encode_sint64` | 8000 packed sint64 values as one-byte (`small_1B`), mostly three-byte (`large_3B`) or exclusively ten-byte (`ten_10B`) varints; scalar against varint-simd where that builds |
| `message` | `message` | tag-dispatch loops with `?` over `mixed`, `fixed_len` and `wide_tags` messages (below), each set eight distinct messages rotated per iteration |

`brokkr bench NAME` measures and saves a baseline named for the commit;
`--commit REF` measures another commit; `--compare A B` reports B against A
without sampling. `brokkr man bench` documents the environment gate that
refuses to compare baselines built under different toolchains or flags.

Criterion compares two separate builds. That answers "did this commit get
faster" only to the extent that the two builds' code layouts are equally
favourable, which the next sections show is not something to assume.

## Layout sensitivity

On this crate's hot loops, where code lands in memory moves timings as much
as the code itself does. Two findings:

- An earlier lab built two copies of `lib.rs` into one binary with raw
  `rustc` and fat LTO and rebuilt it under nine code-alignment
  configurations. Identical code moved 10 to 37% from layout alone.
- The ensemble described below, run on 2026-10-26 (AMD Ryzen 9 9950X3D2,
  cargo 1.101.0-nightly, working tree at c5906ab against baseline 8a450a0),
  measured `decode_packed_sint64_cumulative` on one-byte varints. Its source
  is unchanged between those revisions except for comments and lint
  attributes. Across 18 builds (nine alignment configurations, each as AB and
  BA) the working-tree/baseline median ratio ranged from 0.708 to 5.996.
  `PackedSint64Iter` on ten-byte varints ranged from 0.80 to 1.09, both
  directions, depending on the build.

A single A/B build, criterion or otherwise, can therefore report a large
speedup or slowdown that belongs to the build, not to the change. In the
2026-10-26 run, by contrast, the `?` message loop over `mixed` fields was
faster in the working tree in all 18 measured AB and BA builds (median
ratios 0.91 to 0.97): the kind of result the acceptance rule below is for.

## The same-binary A/B tool: `ab`

`bench/examples/ab.rs` puts a baseline revision and the working tree in one
binary and times them against each other. Its workloads come from the
`workloads!` macro in `bench/src/lib.rs`, instantiated twice in two harness
slots, X and Y, each against a different crate:

- `protohoggr`: the working tree (path dependency).
- `protohoggr_base`: the baseline, a git dependency on this repository pinned
  to a revision in `bench/Cargo.toml`.
- `protohoggr_ctl`: the same commit as the baseline under a second cargo
  identity, for the AA control (below).

Per workload: `packed_sum` (`PackedSint64Iter`, wrapping sum) and
`cumulative` (`decode_packed_sint64_cumulative`) over `small` (one-byte),
`large` (mostly three-byte), `random` (mostly nine- and ten-byte) and `ten_byte`
(ten-byte only) packed sint64; `msg_question` (`?`) and `msg_unwrap` tag
dispatch loops over `mixed` (varint, five-byte bytes, fixed32, skipped fixed64
and varint fields), `fixed_len` (fixed32 and three-byte bytes) and
`wide_tags` (two-byte tags, fixed32 and 130-byte bytes) messages.

Measurement:

- Pinned to one CPU with `sched_setaffinity` (`AB_CPU`, default 2).
- Every input set is eight distinct buffers rotated per call, so no workload
  replays a single buffer. The eight-buffer cycle itself repeats, and a
  branch predictor may still learn much of it.
- Both sides are checked to compute the same result on every input first.
- `time` mode: 41 rounds of 400 calls per side, alternating which side runs
  first; prints the median and p10/p90 of the per-round ratio, the non-baseline
  side over the baseline.
- `pmu` mode (x86-64 only): user-space instructions, cycles and branch
  misses through `perf_event_open`; a count the kernel multiplexed is
  refused, not scaled. Prints the median of nine repeats per side,
  alternating order.
- A filter that matches no workload is an error; `info` mode prints the
  `build:` line and checks results without measuring anything.
- First it prints a `build:` line: which crate each slot holds, the panic
  strategy, whether `--cfg ab_ensemble` reached the build, the enabled target
  features, and the xxh3-128 of the running executable.

```sh
brokkr run ab -- time [FILTER]          # AB: X = baseline, Y = working tree
brokkr run ab -- pmu [FILTER]
brokkr run ab --features swap -- time   # BA: X = working tree, Y = baseline
brokkr run ab --features aa -- time     # AA: X = baseline, Y = control
```

`swap` exchanges which crate each slot is instantiated against. It is a
second build treatment, not a promise that the two implementations traded
physical places: the compiler and linker choose the final function order.

### Choosing the baseline

Change both `rev` values in `bench/Cargo.toml` together: `protohoggr_base`
takes the full 40-character hash, `protohoggr_ctl` a 12-character prefix of
the same commit. Cargo keys a git source by the rev string as written, so the
two spellings are two packages of identical source; `Cargo.lock` shows both,
with different `?rev=` and the same `#` commit. Keep the prefix unambiguous.

The revision must exist on GitHub. Cargo resolves git dependencies for every
workspace build, the library's included, so a local path or `file://` URL
would break every other checkout. Comparing the working tree against an
unpushed HEAD is therefore not possible today; brokkr#36 asks brokkr for a
way to resolve the dependency from a local commit without a push or a
worktree. Until then a comparison against the latest pushed commit answers a
different question than one against local HEAD, and should say so.

### The AA control, and what merging does to it

AA builds two crates of the baseline's source, with the same harness as AB,
so its ratio should be 1 up to noise and layout. Its limits:

- It is identical source under two git identities, not a matched
  path-against-git control.
- LLVM's function merging folds functions that compile to identical code.
  In the 2026-10-26 AA build without ensemble flags only `msg_unwrap` kept
  two copies (its panic locations name two different checkout paths, so the
  copies differ); slot Y's `packed_sum`, `cumulative` and `msg_question` had
  no symbol of their own, and in all nine ensemble configurations their AA
  ratios stayed within half a percent of 1. A collapsed AA says nothing about
  layout robustness; for those workloads there is no AA control, only the AB
  and BA legs.
- Where AA stayed live (`msg_unwrap`), identical code ranged from 0.865 to
  1.099 across the three message sets and nine configurations.

Whether an AA workload is live has to be established in the measured
executable (see "Reading the assembly"), per workload and per build: a
surviving symbol can still be a thunk into a shared body. A diagnostic
ensemble with `AB_EXTRA_RUSTFLAGS=-Zmerge-functions=disabled` (nightly only)
turns off LLVM's function merging, so more copies survive; shared callees
and other folding are still possible, so its AA needs the same inspection.
It changes the optimization policy for the whole build: report it
separately, and never use it to calibrate the default run.

## The layout ensemble

`bench/ensemble.sh <target-triple> [FILTER]` runs the AB, BA and AA legs
under nine alignment configurations - none, `-align-all-functions` 6, 7,
`-align-loops` 64, 32, `-align-all-nofallthru-blocks` 5, and three
combinations - each build and run through `brokkr run`:

```sh
bench/ensemble.sh x86_64-unknown-linux-gnu
bench/ensemble.sh x86_64-unknown-linux-gnu msg_question
```

The flags reach rustc through `CARGO_TARGET_<TRIPLE>_RUSTFLAGS`, which cargo
joins with the `[target.<triple>]` and matching `[target.'cfg(..)']` rustflags
of its config files. `RUSTFLAGS` would not do: cargo takes rustflags from
exactly one source, and `RUSTFLAGS` replaces the config tables entirely,
dropping a host's `-Ctarget-cpu=native` and linker choice. The target
variable in turn masks `build.rustflags`, so the script refuses to run when
`RUSTFLAGS`, `CARGO_ENCODED_RUSTFLAGS`, `CARGO_BUILD_RUSTFLAGS` or
`CARGO_BUILD_TARGET` is set, or when a cargo config file in the chain sets
`build.rustflags`, `build.target` or uses `include`. An existing
`CARGO_TARGET_<TRIPLE>_RUSTFLAGS` is appended to.

Each flagged leg also gets `--cfg ab_ensemble`. A plain build runs first;
every flagged leg must report `ab_ensemble=true` and the plain build's target
features, or the script stops. That proves the flags were injected, and
catches a masked flag that changed the enabled target features. It cannot
see a masked flag that changes neither cfg nor target features (a linker
choice, a `-Ctarget-cpu` whose tuning differs under the same features). The
config check is a line-based approximation of TOML that refuses what it
recognizes. brokkr#37 asks for `brokkr run` to append rustflags itself, the
way `[[check]]` sweeps already do, which would retire both.

Reading the output: the project's acceptance rule is that an effect has the
same sign in every AB and BA leg and, where AA is live for that workload,
lies outside the AA range. That is a criterion, not a proof: a bias of the
path-against-git arrangement could favour one side in every configuration
without AA (git against git) reproducing it, and nine alignment
configurations sample layouts, they do not exhaust them.

## Reading the assembly

`brokkr build ab --release [--features swap|aa]` builds the same executable
`brokkr run` measures and prints a content-addressed copy,
`.brokkr/artifacts/<xxh3-128>/ab`. The `exe-xxh3-128` in a run's `build:`
line names that directory, so a disassembly can be tied to the exact bytes
that were timed. Under ensemble flags, export the same
`CARGO_TARGET_<TRIPLE>_RUSTFLAGS` for the build.

The slot workloads (`ab::linux::slot_x::msg_question` and so on) are
`#[inline(never)]` and are the entry points. `nm -C` shows which survived;
`objdump -d` from each one, following calls and tail jumps into out-of-line
library code (`read_varint_slow`, the cumulative decoder, iterator bodies),
shows whether the two sides' hot loops are separate and where they sit
relative to 64-byte boundaries. For a primitive no workload isolates, add an
`#[inline(never)]` workload to the macro rather than a separate probe binary,
so the probe exists for both sides in one build.
